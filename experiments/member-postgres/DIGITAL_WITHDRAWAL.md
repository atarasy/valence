# Contextual digital withdrawal candidate

The engine now exposes `memberWithdrawalReview` and `withdrawMember`. This is the verification primitive for the upcoming authenticated member HTTP workflow, not a deployed endpoint. `memberWithdrawalScope` must explicitly enable the deployment environment and HTTPS origin, matching the RP ID. Decision and statement scopes alone do not enable withdrawal.

The profile is `atarasy.member-withdrawal-authorisation.1`; the operation request domain is `atarasy.member-withdrawal-operation.1`. Envelope fields and contextual challenge layout follow the existing decision envelope, with distinct profile/domain constants. All authority fields, reviewed revision, canonical action, expiry, key fingerprint and request digest are covered. The engine verifies actual assertion bytes, exact origin, UP/UV and deployment context; it never accepts an arbitrary expected challenge or a verification boolean.

Canonical action bytes are newline-separated `valence.member-withdrawal.1`, offer ID, decided timestamp and decision revision. The revision hashes the JSON array `["valence.member-decision-generation.1", offer ID, decided timestamp, candidate tuples, retained confirmation tokens]`. Each candidate tuple is `[id, valence, kept_as, lineage, decided_at]` in the stored offer order. The confirmation register is retained after withdrawal and grows with each new signature, so even identical choices made again at the identical timestamp cannot accept the previous generation's withdrawal proof. Only the digest is exposed by the review helper; raw confirmation tokens are not returned.

The internal withdrawal state transition remains shared with the existing protocol path: a signed, unsettled digital decision is required for the contextual entry point; cooling restrictions and settlement finality still apply. The legacy withdrawal API does not accept contextual assertions. The existing legacy canonical protocol has not been changed by this candidate.

Six focused tests cover valid withdrawal, legacy-route separation, same-choice/same-millisecond redecision replay, explicit deployment opt-in, physical binding refusal, current-generation binding, tampered context, foreign origin, missing UV, expiry, no cooling, closed cooling and settled refusal. All 296 engine tests and the engine strict typecheck pass.

## Authenticated PostgreSQL workflow

`POST /member/withdrawals/prepare` accepts exactly `{decisionOperationID}`. The existing `/member/operations/{id}` review, submit, cancel and outcome routes dispatch withdrawal operations by their saved kind. The original committed decision must belong to the current session/credential/mandate/presenter grant and current journal incarnation. Its saved result must match the engine offer, and its retained decision-generation digest must match the engine's current generation.

Preparation saves the original decision review, original result/operation association, current mandate, current incarnation and engine eligibility. Eligibility includes the canonical generation and cooling deadline. No cooling or a closed window fails before a passkey is requested. A mandate lapse or offer expiry does not itself shorten an existing cooling right. Preparation expiry is bounded by the session, configured ceremony lifetime and cooling deadline. Changed review requires cancellation and a fresh preparation; expired unsigned preparation can be replaced.

Submit verifies the fresh snapshot, contextual passkey and shared credential counter inside the existing PostgreSQL deployment transaction. It invokes `withdrawMember`, freezes the original withdrawal result, commits the withdrawal journal and advances incarnation within that unit. Failure even at the final head write rolls back the engine, counter, result, journal and head. Exact repeated submission returns the same original result; a different assertion cannot claim it. Readback is `{operationID, operationState, withdrawal}`, with null before commitment and `{decisionOperationID, nextIncarnation, offer}` after commitment. The offer is the historical post-withdrawal snapshot, never current order/payment status. Neither redecision nor later settlement rewrites that snapshot or the original decision outcome.

New committed decision reviews retain their engine generation atomically. Historical records lacking that metadata still read through their original outcome API but cannot infer an association to the current engine generation for withdrawal. No deployed digital records have been migrated or accepted here. Native withdrawal UI and real-device acceptance remain outstanding.

Validation adds eight HTTP scenarios covering concurrent submit, same-timestamp redecision, immutable old outcomes, cancellation, expiry/replacement, cooling boundaries, lapsed mandate, valid other-household denial, credential revocation, changed review, lost response and restarted readback, final-write rollback with same-counter retry, and out-of-band identical-content redecision. The latter would be indistinguishable by offer fields alone; retained generation prevents the original operation being substituted. All 511 engine/member tests and strict typechecks pass. The optional `ATARASY_WITHDRAWAL_FIXTURE_OUTPUT` capture writes synthetic public responses only, refuses overwrite and excludes bearer tokens, assertions and private keys, for the upcoming native integration.

No provider or operational gate is involved. No hosted deployment has occurred.

## Durable journal incarnation foundation

Migration `0002_powerful_shinobi_shaw` replaces the blocking-operation index with uniqueness on deployment, offer, decision incarnation and action slot. Decision and withdrawal each have one blocking operation per incarnation. Physical statements always use incarnation zero and the decision slot, regardless of an invalid caller-supplied incarnation; their original one-per-offer constraint remains. Existing rows without an incarnation are zero. The migration rewrites no operation payload.

`member_decision_heads` records the current incarnation and the committed decision/withdrawal pair that advanced it. A head is usable only if both referenced records are committed for the prior incarnation, offer and matching authority. Preparing a withdrawal requires a committed current decision. The trusted `advanceAfterWithdrawal` adapter method checks owned matching committed records, advances once, accepts exact repetition and refuses an older pair after a later advance. It does not cryptographically verify a withdrawal or call the engine; the HTTP adapter does that within the same PostgreSQL transaction. This method has no public route.

Historical operation states, receipts and response records remain committed and readable. They are neither deleted nor relabelled cancelled. Decision preparation searches only its current incarnation. For successors, that incarnation enters the sealed decision snapshot and therefore its reviewed revision and contextual assertion; incarnation zero keeps the previous snapshot/request hash representation. No existing physical hash changes.

The journal tests use explicitly synthetic trusted proof digests to isolate storage guarantees. They exercise concurrent preparation, old records without the optional field, two successive advances, stale-pair refusal, original HTTP outcome readback, restart, same-slot database uniqueness, unchanged physical uniqueness, enclosing-unit rollback and corrupt-head refusal. All 503 tests across engine/member suites pass, with strict HTTP test typechecking. These journal-only probes are separate from the cryptographic HTTP tests above; neither establishes native workflow acceptance. Local migration is tested only on the disposable development database; no hosted database has changed.
