# PostgreSQL operational snapshot candidate

`captureDeployment(pool, identity)` takes the same control-row lock as application writers and returns every engine row for that deployment in original insertion order. It includes all namespaces: quotations, fixed protections, original confirmations, operation/review history, decision incarnation heads, authority grants, credentials, passkey counters and sessions. Values remain their exact stored JSON strings. It does not reconstruct state from public surfaces or reset uncertain operations.

`restoreDeploymentCandidate(pool, snapshot, expectedIdentity)` requires the same deployment identifier, environment, HTTPS origin and epoch. The destination database must already have matching tables, columns, constraints and indexes; extra tables or non-internal triggers refuse capture/restoration. A deployment that already exists cannot be overwritten, even when disabled. Control and all rows are inserted in one transaction and read back before commit. Insertion order is preserved while database-generated ordinal numbers are local to the destination.

The restored control row is always disabled. Neither capture nor restoration enables the destination, disables the source, changes an epoch, switches routing or contacts a provider. A live capture is a point-in-time backup; later source writes make it stale for cutover. Activating a candidate requires a separate fenced cutover procedure and evidence that the old writer can no longer act. Changing origin or RP is not supported by copying credential records.

These are trusted administrative APIs, never member routes. The returned snapshot contains sensitive authentication and household records and must be handled as a database backup. The digest detects accidental changes and is not proof of provenance or a signature. The functions do not accept an arbitrary archive as authority, repair corrupt application records, or claim that schema equality proves semantic validity. The caller must obtain it from the trusted source database. No snapshot content is logged or written to disk by these APIs.

Tests use isolated synthetic PostgreSQL databases. They cover an active writer barrier, exact ordered round-trip, disabled destination fencing, concurrent restores, existing-target refusal, changed scope/digest/schema, and rollback after the first inserted row. An HTTP integration test carries a committed digital decision and withdrawal plus a prepared successor through the candidate, uses `freezeDeployment` to fence the synthetic source before capture, and explicitly enables the test destination. It verifies both immutable outcomes, exact prepared review, retained quotation/incarnation, rejection of the old passkey counter and successful approval with the next counter. This test-only activation is not an implementation of a production cutover.

Remaining work includes a complete writer-fenced cutover/rollback protocol, operator transport and storage of sensitive backups, PostgreSQL deployment acceptance, and native host switching. The older SQLite snapshot code remains a separate implementation with its own coverage limits.

## Atomic source freeze

`freezeDeployment(pool, identity, ticket, runtimeFingerprint)` waits on the application writer lock, writes a durable `member_writer_migration/current` ticket, disables the source and captures the final snapshot in one transaction. The caller supplies a UUID ticket before the operation so a lost response can be recovered using the same ticket. The runtime fingerprint is a pinned 64-character SHA-256 value supplied by trusted orchestration. It is retained and compared, not computed from the running server by this API.

The ticket records the schema and digest of all pre-freeze rows. A matching retry returns the same frozen snapshot; a different ticket/runtime, changed source content, enabled control, or unrelated administrative disable is refused. Failure before commit rolls back both ticket and disable. Ordinary application writes and `initialiseDeployment` refuse the disabled source. Concurrent freeze tickets have one winner.

This adds source preparation, not destination activation or cancellation. There is deliberately no general “enable source” API: enabling an old source after another target starts would permit duplicate writers and lose newer data. Next steps are binding one concrete destination to the ticket, retiring the source before destination activation, and defining recovery at each stage. Administrative direct SQL remains outside application fencing guarantees.
