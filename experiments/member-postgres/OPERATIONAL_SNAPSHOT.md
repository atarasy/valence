# PostgreSQL operational snapshot candidate

`captureDeployment(pool, identity)` takes the same control-row lock as application writers and returns every engine row for that deployment in original insertion order. It includes all namespaces: quotations, fixed protections, original confirmations, operation/review history, decision incarnation heads, authority grants, credentials, passkey counters and sessions. Values remain their exact stored JSON strings. It does not reconstruct state from public surfaces or reset uncertain operations.

`restoreDeploymentCandidate(pool, snapshot, expectedIdentity)` requires the same deployment identifier, environment, HTTPS origin and epoch. The destination database must already have matching tables, columns, constraints and indexes; extra tables or non-internal triggers refuse capture/restoration. A deployment that already exists cannot be overwritten, even when disabled. Control and all rows are inserted in one transaction and read back before commit. Insertion order is preserved while database-generated ordinal numbers are local to the destination.

The restored control row is always disabled. Neither capture nor restoration enables the destination, disables the source, changes an epoch, switches routing or contacts a provider. A live capture is a point-in-time backup; later source writes make it stale for cutover. Activating a candidate requires a separate fenced cutover procedure and evidence that the old writer can no longer act. Changing origin or RP is not supported by copying credential records.

These are trusted administrative APIs, never member routes. The returned snapshot contains sensitive authentication and household records and must be handled as a database backup. The digest detects accidental changes and is not proof of provenance or a signature. The functions do not accept an arbitrary archive as authority, repair corrupt application records, or claim that schema equality proves semantic validity. The caller must obtain it from the trusted source database. No snapshot content is logged or written to disk by these APIs.

Tests use isolated synthetic PostgreSQL databases. They cover an active writer barrier, exact ordered round-trip, disabled destination fencing, concurrent restores, existing-target refusal, changed scope/digest/schema, and rollback after the first inserted row. An HTTP integration test carries a committed digital decision and withdrawal plus a prepared successor through the candidate, uses the implemented source freeze and bound destination activation. It verifies both immutable outcomes, exact prepared review, retained quotation/incarnation, rejection of the old passkey counter and successful approval with the next counter. This is a synthetic database rehearsal, not deployed cutover evidence.

Remaining work includes abort and subsequent/reverse migration, operator transport and storage of sensitive backups, routing, PostgreSQL deployment acceptance, and native host switching. The older SQLite snapshot code remains a separate implementation with its own coverage limits.

## Atomic source freeze

`freezeDeployment(pool, identity, ticket, runtimeFingerprint)` waits on the application writer lock, writes a durable `member_writer_migration/current` ticket, disables the source and captures the final snapshot in one transaction. The caller supplies a UUID ticket before the operation so a lost response can be recovered using the same ticket. The runtime fingerprint is a pinned 64-character SHA-256 value supplied by trusted orchestration. It is retained and compared, not computed from the running server by this API.

The ticket records the schema and digest of all pre-freeze rows. A matching retry returns the same frozen snapshot; a different ticket/runtime, changed source content, enabled control, or unrelated administrative disable is refused. Failure before commit rolls back both ticket and disable. Ordinary application writes and `initialiseDeployment` refuse the disabled source. Concurrent freeze tickets have one winner.

This function prepares the source; destination activation is described below. There is deliberately no general “enable source” API: enabling an old source after another target starts would permit duplicate writers and lose newer data. The activation API below binds one concrete destination to the ticket and retires the source before destination activation. Administrative direct SQL remains outside application fencing guarantees.

## Bound destination activation

`activateDeploymentCandidate(sourcePool, targetPool, identity, ticket, runtimeFingerprint)` acquires the frozen source lock and gives the disabled target a newly generated local instance identifier. Registration commits before retirement so interruption cannot lose that identity. The source is then durably marked retired with exactly that instance while still disabled. Only after that commit does the target atomically record activation and enable its control row. Each phase rechecks the ticket, runtime, schema and original content.

A retry accepts the same retired source and target instance. Once the target is active, its application contents may legitimately advance; retries validate the durable activation receipt rather than requiring the old content hash. An independent second restoration has a different instance and cannot activate the retired ticket. The restore API refuses snapshots containing a target-instance record, preventing the normal restore path from cloning that identity. Administrative SQL or a whole database clone is outside this guarantee.

Failures before retirement leave the source frozen. Failures after retirement leave it retired and the target either ready or already active. Lost commit acknowledgements are resolved by repeating this exact transition. There is no source re-enable or destructive retry. Multiple database transactions intentionally favour a period with no writer over two writers.

The synthetic HTTP integration now uses both real freeze and activation APIs: no test-only SQL enables the target. Tests also cover two destination candidates racing, changed destination content, failure after retirement, repeated activation after new target writes, and lost source/target commit acknowledgements.

Routing, deployed runtime fingerprint attestation, operator backup transport, abort-before-retirement, and a subsequent/reverse migration remain open. In particular, an activated target carries its local instance and cannot yet be fed back into generic restoration; a subsequent move needs a new migration lifecycle with retained history rather than copying that instance. This is same-origin, same-deployment infrastructure migration, not cross-origin passkey portability.
