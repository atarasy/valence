# Authenticated digital decisions

This candidate adds `POST /member/decisions/prepare` with `{offer, decisions}` and uses the existing account-scoped `/member/operations/{id}` read, submit, cancel and outcome routes. Every candidate must explicitly be kept for self or returned. A missing choice is not refusal. Onward gifting is outside this native increment.

The prepared profile is `atarasy.member-decision-authorisation.1`. Its challenge hashes `[profile, JSON.stringify([1, environment, origin, rpID]), operationID, requestDigest, reviewedRevision]`. The request digest hashes the JSON array beginning with `atarasy.member-decision-operation.1`, followed by the existing journal scope, principal, credential, household, key fingerprint, offer, mandate, presenter, canonical decisions, reviewed revision and expiry. The canonical decisions retain the existing protocol bytes. Physical statement, legacy decision and digital contextual assertions cannot substitute for each other.

Preparation verifies session, credential/mandate binding, ownership, presenter grant, digital state, all choices, catalogue prices/parties, disclosure signatures, deliberation, carriage and expiry. The frozen review includes the approval, full mandate, exact decisions and goods/carriage totals in supplied units; it does not invent currency. Delivery code remains internal to the sealed snapshot. No complete review is offered while carriage is unknown.

Submission holds the existing PostgreSQL deployment lock. It rechecks the sealed revision, verifies the passkey and shared counter, claims the journal, calls the engine's contextual decision method and stores the original result in one database transaction. No provider call is made. Any database failure rolls back all effects and the counter. The engine also independently verifies the exact origin, scope, profile, key fingerprint, content digest and expiry. No contextual decision is accepted without an explicit configured `memberDecisionScope`.

The outcome is `{operationID, operationState, decision}`; the decision is null before commitment. A committed result is a frozen historical offer snapshot, not a payment receipt or the current mutable offer. Reopening the service, losing a submit response or retrying the identical assertion returns that original result. Another assertion cannot claim it. Revoked or unrelated member authority cannot read it. A committed operation cannot be cancelled. Expired unsigned preparations can be replaced; changed choices require cancellation and new review.

The existing `member_operations` unique index covers both operation kinds without schema migration. Physical operation hashes and their stored records keep their previous form. Digital reviews have an explicit profile and are rejected by the physical reader.

## Validation and limits

Engine tests cover valid explicit decisions, disabled scope, physical/digital separation, partial/duplicate/foreign candidates, content and authority tampering, wrong origin, missing UV, expiry and legacy-route refusal. PostgreSQL HTTP tests exercise independent concurrent compositions, original-result recovery after later settlement, cancellation and expiry replacement, changed review, a valid foreign-household session, missing carriage, zero-charge explicit refusal with a discarded response, and a scoped database write fault with successful same-counter retry after rollback.

This candidate has not been deployed or connected to the native draft UI. The current presenter API rejects digital delivery writes; a permitted carriage-quotation path is still required for end-to-end preparation with known carriage. Tests use synthetic trusted carriage records, not a completed merchant workflow. Native independent review decoding, contextual challenge reconstruction, protected journal, signing, recovery and digital withdrawal/redecision remain required. The current blocking-operation invariant retains committed decisions; implementing withdrawal must preserve historical outcomes while deliberately permitting a new decision incarnation. No pilot or full-product completion is claimed.
