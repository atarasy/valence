# Authenticated digital decisions

This candidate adds `POST /member/decisions/prepare` with `{offer, decisions}` and uses the existing account-scoped `/member/operations/{id}` read, submit, cancel and outcome routes. Every candidate must explicitly be kept for self or returned. A missing choice is not refusal. Onward gifting is outside this native increment.

The prepared profile is `atarasy.member-decision-authorisation.1`. Its challenge hashes `[profile, JSON.stringify([1, environment, origin, rpID]), operationID, requestDigest, reviewedRevision]`. The request digest hashes the JSON array beginning with `atarasy.member-decision-operation.1`, followed by the existing journal scope, principal, credential, household, key fingerprint, offer, mandate, presenter, canonical decisions, reviewed revision and expiry. The canonical decisions retain the existing protocol bytes. Physical statement, legacy decision and digital contextual assertions cannot substitute for each other.

Preparation verifies session, credential/mandate binding, ownership, presenter grant, digital state, all choices, catalogue prices/parties, disclosure signatures, deliberation, carriage and expiry. The frozen review includes the approval, full mandate, exact decisions and goods/carriage totals in supplied units; it does not invent currency. The digital quotation (offer, amount and original timestamp) remains inside the sealed snapshot; it contains no delivery code or parcel status. No complete review is offered while carriage is unknown.

Submission holds the existing PostgreSQL deployment lock. It rechecks the sealed revision, verifies the passkey and shared counter, claims the journal, calls the engine's contextual decision method and stores the original result in one database transaction. No provider call is made. Any database failure rolls back all effects and the counter. The engine also independently verifies the exact origin, scope, profile, key fingerprint, content digest and expiry. No contextual decision is accepted without an explicit configured `memberDecisionScope`.

The outcome is `{operationID, operationState, decision}`; the decision is null before commitment. A committed result is a frozen historical offer snapshot, not a payment receipt or the current mutable offer. Reopening the service, losing a submit response or retrying the identical assertion returns that original result. Another assertion cannot claim it. Revoked or unrelated member authority cannot read it. A committed operation cannot be cancelled. Expired unsigned preparations can be replaced; changed choices require cancellation and new review.

The existing `member_operations` unique index covers both operation kinds without schema migration. Physical operation hashes and their stored records keep their previous form. Digital reviews have an explicit profile and are rejected by the physical reader.

## Validation and limits

Engine tests cover valid explicit decisions, disabled scope, physical/digital separation, partial/duplicate/foreign candidates, content and authority tampering, wrong origin, missing UV, expiry and legacy-route refusal. PostgreSQL HTTP tests exercise independent concurrent compositions, original-result recovery after later settlement, cancellation and expiry replacement, changed review, a valid foreign-household session, missing carriage, zero-charge explicit refusal with a discarded response, and a scoped database write fault with successful same-counter retry after rollback.

The native candidate at Atarasy fef6726 implements independent review decoding, contextual challenge reconstruction, saved operations, signing and recovery. This service candidate has not been deployed. Digital carriage now uses the authenticated quotation route below; digital delivery writes remain refused. Merchant screen and physical-device acceptance, digital withdrawal/redecision and the separate private-node requirements remain open. The current blocking-operation invariant retains committed decisions; implementing withdrawal must preserve historical outcomes while deliberately permitting a new decision incarnation. No pilot or full-product completion is claimed.

## Digital carriage quotation

`POST /presenter/offers/{id}/carriage-quote` accepts exactly `{carriage}` under the existing presenter credential. It resolves offer ownership before reading or writing the quote; another presenter sees the same 404 as an absent offer. The amount must be a nonnegative safe integer. A first quote requires an unexpired digital offer in drafted or presented state. Physical boxes continue to use delivery.

A quote is stored separately in the hub's `carriage_quotes` register and never creates a delivery, carrier code, placement or shipment status. The first successful write returns 201 with `{offer, carriage, quoted_at}`. An identical retry returns 200 and the original timestamp, including after a decision; another amount returns 422 `carriage_fixed`. A mistaken quote requires a new offer. Query parameters, extra fields and caller-supplied timestamps are refused. Presenter detail includes `carriage_quote`, while `delivery` stays null until a real delivery exists through an independently permitted path.

The PostgreSQL member runtime reads digital approval carriage exclusively from quotes, with no fallback to a delivery row. Physical approvals and statements retain their delivery source. Decision preparation freezes the quote in its review revision; changed trusted quote data invalidates submission. The default reference engine retains its prior delivery-based approval reader unless a deployment configures the separate approval-carriage source. This is deployment functionality; carrying quotes through household export/import is still required before host-move completion.

Vox exposes `/api/offers/{id}/carriage-quote` under `offer:write`, with its existing organization credential, CSRF and audit boundary. Zero additionally requires explicit `carriage_included: true`; that UI-facing flag is not sent to Valence. No delivery or collection permission substitutes for offer authority. Optional `VOX_TEST_SOURCE=/absolute/path/to/vox` enables a cross-repository HTTP test against a disposable PostgreSQL deployment: real Vox handler/client -> authenticated Valence quote -> member approval -> preparation -> synthetic passkey verification -> original decision result. No provider is involved.
