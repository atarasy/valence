# Development device acceptance operator

This trusted CLI is not imported by the deployed API entry. It uses the existing dedicated development database, control-row fence and configuration binding. No migration, HTTP administration route or synthetic passkey is added. Preparation creates one random test principal with empty presenter grants and **no household**; it creates no offer or mandate ownership. A household's identifier is the name of the key its statements are signed with (§13.2, question 55), and on this service that key is the passkey the device registers, so the principal adopts its household at the `statement` step and not before.

Run from the service repository with the existing Vercel production-slot environment file. That slot belongs to the development-only project. Keep its contents private.

```sh
NEON_PROJECT_ID=young-pond-73223516 bun --env-file=/absolute/private/.env.production.local experiments/member-postgres/deployment/device-acceptance.ts status
NEON_PROJECT_ID=young-pond-73223516 bun --env-file=/absolute/private/.env.production.local experiments/member-postgres/deployment/device-acceptance.ts prepare
NEON_PROJECT_ID=young-pond-73223516 bun --env-file=/absolute/private/.env.production.local experiments/member-postgres/deployment/device-acceptance.ts invite /absolute/private/new-invitation.json
NEON_PROJECT_ID=young-pond-73223516 bun --env-file=/absolute/private/.env.production.local experiments/member-postgres/deployment/device-acceptance.ts statement
```

Run preparation once; a repeated preparation refuses. Status reports the existing identifiers, grants and active credential count, and the statement record once it exists. Invitation issuance checks the active principal, its household (still unclaimed at this point) and empty grants within the same locked unit. A change refuses issuance. The existing enrolment service issues a single-use invitation with the configured five-minute lifetime. Generate it only when the device is ready.

The output invitation file must not exist. Exclusive creation with mode 0600 refuses overwrite and symlink targets. The token is never printed on stdout. Supply it locally in the app's invitation field and delete the local file after use or expiry. Do not commit it, paste it into acceptance logs or send it to another person. If commit or file output fails, inspect status and expiry before an explicit fresh issuance; the CLI never retries automatically.

The isolated Neon verification test prepares the account, refuses a duplicate, completes synthetic registration through the public HTTP handler, refuses invitation replay, observes one credential, then refuses status/issuance after presenter grants change. This is service evidence only. Actual iPhone/iPad registration still requires the system credential UI and the user's verification.

## Statement approval acceptance

`statement` runs once, after the device has registered exactly one passkey **and signed in with it at least once**. Registration alone proves nothing: enrolment runs with `attestationType: 'none'`, so the registered public key is a value the client sent and no signature covers it, and the household this step adopts is the name of that key. **Exactly one credential, and it must have signed.** Once the household is adopted the principal takes no further credential at all, which is enforced where a credential is added rather than counted at this step: an enrolment ceremony held open across this step and finished afterwards used to produce a credential that read the household's session, offers, settlement statement and mandate terms with nothing proved. A second credential beside a signed-in one is refused rather than ignored: it would otherwise read the household's session, offers, settlement statement and mandate while having proved nothing. `statement` names how many have signed in and how many have not, and `retire` undoes the enrolment step by revoking **every** active credential, signed-in ones included, and dropping every invitation and half-finished ceremony the acceptance principal has outstanding, so the device can be invited again. The credential and passkey rows are **removed** rather than marked revoked, because a row left behind makes the same device's credential id unusable for the life of the deployment, which is the opposite of what this action is for. Nothing has been adopted before this step, which is why revoking all of them is safe; `retire` refuses once a statement exists. In one locked unit it registers a development presenter and merchant with ephemeral Ed25519 keys whose private halves are dropped, a signed catalogue with one physical product at 1,200 and a signed disclosure saying no goods ship and no payment is taken. It derives the household's identifier from the registered passkey's own P-256 public key, adopts it onto the principal once, registers that key under the household's name and imports the mandate `<household>.1` (a mandate has no key of its own, so nothing is registered under a mandate's name), creates and presents one physical box, records a delivery with carriage 550 and a collection marking the goods consumed. It grants the presenter, binds mandate and offer ownership, and binds the mandate to that credential.

The binding service derives its context from a live session, so the unit creates a session for the credential, binds, and revokes that session before commit. The token never leaves the unit. Changing the grant also revokes the device's current session, so the device signs in again before it sees the box.

Nothing here signs the statement. Approval still needs the native assertion from the registered passkey through `/member/statements/prepare` and `/member/operations/{id}/submit`. The settlement is an engine record in the development database; no provider is called and no money moves. A repeated `statement` refuses, and with zero or several active credentials it refuses before writing.

`statement-acceptance.test.ts` exercises this end to end on an isolated database: synthetic registration, the operator step, sign-in, list, statement read, prepare, submit and outcome. Two negative controls were run in disposable copies: removing the mandate binding and keeping the internal session live each make the test fail.

## Further boxes

**Read a failure's reason.** The command prints its own reasons and the engine's and the store's, and prints `unknown (the failure did not come from this tool)` for anything else, which includes the driver: a connection or authentication failure looks like that and says nothing about what it was. A fenced deployment says so in words.

**The mandate is signed by the device, not by this step** (question 56, decided 2026-09-18; question 58, decided 2026-09-19). The first `statement` writes the mandate as a claim, which is what an import writes, and stops with `awaitingSignature`: a claim has no effect, so no offer can name it yet. The device then lists the claim at `/member/mandates/list`, asks `/member/mandates/prepare` for the passkey challenge, which is the SHA-256 of `valence.mandate.2`, this deployment's relying party and the claim's fields, and sends its assertion to `/member/mandates/submit`. Run `statement` again afterwards and it presents the box. The claim's terms are written here: the out-of-network ceiling is one box's price, which is the quantity §16.2 bounds and carriage is not in it, and **it bounds nothing here**, since no registry is supplied, the engine reads every merchant as in network and the out-of-network total is always zero (a second refutation pass set it to 0 and the whole acceptance still ran). The other three fields are the widest the shape allows on purpose: a cooling window would stop the acceptance settling, a daily ceiling would stop the second box, and a co-signer is a key nobody holds. **What the device signs is what it can read before it signs**, and what contains the rest is that this is a development deployment: do not run it against a device whose passkey is or will be a real member's.

**The order on a device, since 2026-09-19.** `statement` (writes the claim) → the device signs the claim (list, prepare, submit) → `statement` again (presents the box) → the device signs the settlement statement (`/member/statements/prepare`, `/member/operations/{id}/submit`) and reads the outcome. **A set whose every line is returned settles at 0 at the moment it is decided** (question 62), so a device that declines everything should show it settled rather than waiting for a presenter; a physical box stays `decided` until its collection is recorded, which `statement` does, so the acceptance box never reaches that case.

**An acceptance prepared before 2026-09-16 has a free-name household and cannot adopt one.** `statement` refuses it, and the command prints the reason (`Acceptance household is not this credential`) after the fixed failure line. There is no command that clears it, and clearing it by hand would destroy the record of what was actually done under the old rules. **Start a second deployment instead**: `deployment/identity.ts` names the logical deployment, rows are keyed by it, and a new id is a clean namespace in the same database. That is what happened on 2026-09-18, when `atarasy_api_dev` was disabled in `atarasy_member.control` and `atarasy_api_dev_2` was bootstrapped and deployed; the first deployment's 149 rows, including nine settled acceptance boxes, are untouched. Bootstrap the new id before deploying the bundle that names it, or every request fails until the control row exists.

`box` adds one more physical box under the mandate and credential binding that `statement` created, with the same price, carriage and consumed collection. It exists for device checks that need a fresh statement each time, such as an interrupted network or a relaunch after approval. A presenter may not offer a household the same product twice (§5.1), so each box registers its own presenter, merchant and one-product catalogue with ephemeral keys, and the grant moves to that presenter. Moving the grant revokes the device's session, so the device signs in again before it sees the box. It refuses unless the latest box has settled, so at most one statement waits at a time, and it refuses if the principal's grants have changed. Status reports the latest box.
